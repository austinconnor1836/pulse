# W18 — Multi-variant day plans

**Branch:** `w18-multi-variant-day-plans` · **Area:** supabase (+ shared) · **DependsOn:** W2, W6
**Status:** specify

## Problem
Today's planned `plan-day` Edge Function (W6) returns **one** `PlanDayResponse` per request,
shaped by the caller's chosen `optimizeFor`. A user opening the Planner has to guess: do they
want a meet-people day? a recovery day? a novelty day? Each guess costs another round-trip and
the user never *compares* — they just pick the first acceptable plan.

W18 introduces a multi-variant wrapper: one request, **N day plans** in parallel, one per
`OptimizationTarget`. The Planner UI can then show a carousel / side-by-side compare ("a
novelty day vs. a meet-people day vs. a recovery day"), making the user's choice deliberate
rather than blind.

Distinct from multi-DAY trip planning (3-day visit, cross-day novelty constraints) — that is
its own post-MVP feature; W18 is **same-day, multiple variants**.

## Exploration findings (what already exists — do NOT rebuild)
- **`OptimizationTarget` enum is canonical** at `shared/src/commonMain/kotlin/com/austinconnor/pulse/shared/Types.kt:141` with `@SerialName` wire values: `"balanced"`, `"meet-people"`, `"novelty"`, `"enjoyment"`, `"recovery"`.
- **`PlanDayRequest` already accepts `optimizeFor: OptimizationTarget? = null`** (`Types.kt:189`). Each variant is *just* a plan-day call with that field set.
- **`PlanDayResponse` already carries `optimizeFor: OptimizationTarget`** (`Types.kt:221`) — every response is self-describing about which target produced it. The wrapper does not need to add a "label" field.
- **`plan-day/index.ts` today is a stub** (`supabase/functions/plan-day/index.ts:36-56`) returning a hardcoded `PlanDayResponse`. W18 cannot reuse what W6 hasn't built yet — implementation is **stacked on W6**, but specification can be done now (the contract is settled by `Types.kt`).
- **Edge Function pattern:** `Deno.serve(async (req) => …)` + `_shared/cors.ts` + a local `json()` helper (`plan-day/index.ts:26-69`). New `plan-day-variants` mirrors that shape verbatim.
- **The "balanced" target is the existing default** when `optimizeFor` is omitted (`plan-day/index.ts:40`). For W18's *default variant set*, "balanced" is therefore the *least* useful variant to include — the user already gets it via plain `plan-day`. The default set is the 4 non-balanced targets.

## Requirements (each traces to a fragment)
- **R1 (→1,4):** New types in `Types.kt`: `data class PlanDayVariantsRequest(val plan: PlanDayRequest, val targets: List<OptimizationTarget>? = null)` and `data class PlanDayVariantsResponse(val variants: List<PlanDayResponse>)`. Mirrored in `shared/types.ts` (W2 contract).
- **R2 (→1,3):** New Edge Function `supabase/functions/plan-day-variants/index.ts` that: parses `PlanDayVariantsRequest`, resolves targets (provided or default), invokes the plan-day core once per target *in parallel*, assembles `PlanDayVariantsResponse`.
- **R3 (→2):** Default targets constant `DEFAULT_VARIANT_TARGETS = ["novelty", "meet-people", "enjoyment", "recovery"]` — exported from the variants module, referenced (not duplicated) by tests + docs.
- **R4 (→3):** Refactor `plan-day/index.ts` so its orchestration is exported as a callable (`planDay(req: PlanDayRequest): Promise<PlanDayResponse>`) consumed by both the `plan-day` HTTP handler and the `plan-day-variants` wrapper. Behavior-preserving — this is part of W6's scope or a separable conformance refactor, not new feature work.
- **R5 (→5):** Validation in the wrapper handler before invoking plan-day: empty `targets`, unknown target string, duplicate target, all → 400 with a named error. Missing `dateISO`/`anchorLocation` is not re-validated; the first plan-day call surfaces it.

## Story-local rules (resolved decisions)
- **D1 — Wrapper endpoint, not a flag on plan-day.** `plan-day-variants` is its own function. Rejected alternative: adding `variants?: OptimizationTarget[]` to `PlanDayRequest`. Reasons: (a) clean cache key per-variant request shape, (b) keeps the single-plan `PlanDayResponse` shape from drifting into a sometimes-array union, (c) deprecation is independent, (d) the wrapper mirrors `plan-day`'s code shape exactly so the cost is trivial.
- **D2 — Default set is the 4 non-balanced targets.** `"balanced"` is already the default the user gets from plain `plan-day`; including it in the default variant set would offer no contrast. Excluding it keeps the carousel meaningful. (Callers can still request `targets: ["balanced", "novelty"]` explicitly.)
- **D3 — Parallel invocation, not serial.** The plan-day core has no shared mutable state between calls (it's pure orchestration over Places + scoring), so `Promise.all(targets.map(t => planDay({...req, optimizeFor: t})))` is safe and ~Nx faster than serial. If a single variant fails, the whole request fails — partial results are worse than re-asking with fewer targets.
- **D4 — Reuse the existing `_shared/cors.ts` + `json()` helper pattern** verbatim from `plan-day/index.ts:64-69`. This is the canonical Edge Function shape.

## Resolved Questions
- *Wrapper endpoint vs. flag on existing plan-day?* → Wrapper endpoint (D1).
- *Should "balanced" be in the default set?* → No (D2).
- *Parallel vs. serial fan-out?* → Parallel (D3).
- *Cross-variant venue dedup (ensure no spot appears as pick in 2+ variants)?* → **Out of scope for W18.** Adds combinatorial cost (each variant must re-rank without the others' picks) and the product value is unclear — sometimes the same spot is genuinely the right pick for two different optimization targets. Listed as a follow-up.
- *Client UI (iOS carousel / Android pager)?* → **Out of scope for W18.** W18 ships the backend contract. UI belongs in W16/W17 follow-ups or a new client item (e.g. W19 Planner-variant carousel).
- *Multi-day trip planning?* → **Distinct feature, not W18.** That requires cross-day novelty constraints, accommodation modeling, energy arcs. Separate post-MVP item.

## Open product/UX questions
- None for the backend contract. The carousel UX is a separate client item; how it surfaces (swipe-through / side-by-side / collapsible cards) is for that item's spec.

## Out of scope
- Cross-variant venue dedup (see Resolved Questions).
- Client UI consuming the new endpoint (separate item).
- Multi-day trip planning (distinct feature).
- Caching of variant responses (Edge Function caching is a cross-cutting concern, not W18-specific).
- Per-variant cost / token budget controls (W4 Claude-judge client is the right home for that).
